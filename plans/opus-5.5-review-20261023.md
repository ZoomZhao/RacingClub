全部 11 条问题都直接对照代码核实过。我没有修改任何文件，`git status` 为空。没有运行 Gradle、npm、Swift 测试，没有构建，也没有使用任何设备或模拟器。执行过的只有只读命令：`git log`/`git show`、`cmp`（确认三份 game-data.json 逐字节相同）、`sips`（读取图片尺寸），以及几段 `node -e` 读取 JSON 做离线统计。

## 总体判断

- **规则核心是可靠的。** Kotlin 的 `Rules.trace`（`Game.kt:49-82`）和 Swift 的 `trace` 用"拼板、入口端口、跨障进度"作为搜索状态，重复跨障、回环、7 号双路、分岔都处理正确。有重叠时不能通关。关卡数据只有一个来源，导出后两端逐字节一致。
- **交互的基础设计合理。** 按下即选中、超过阈值才算拖动、取消不提交、成功一步写一次撤销快照，都没问题。问题集中在两处：选中状态没有退出方式，以及拖动提交依赖全局的 `selected`。
- **架构上最大的耦合是 `GameState`。** 它在 `MainActivity.kt:80-117` 里同时负责对局状态机、计时、存档和排行榜写入，并且依赖 Context，导致最关键的会话逻辑只能靠仪器测试覆盖。iOS 又在 `RacingClubApp.swift:10-44` 平行写了一份，两边已经出现行为差异。
- **测试数量够，但有两个缺口。** 真实数据回放和会话逻辑都不在 CI 里。另外有两条 UI 测试把当前的回退行为写成了期望：一条要求满盘时操作条必须压在拼板自身上，一条把"重建后回到首页"当作正确结果。

## 必须修复

### F-01 [P1] 拼板接近铺满时，操作条压在当前拼板上，遮住道路，而且无法关掉
- **位置**：`BoardInteraction.kt:63-69`（140×52dp 的外置操作条只要碰到任何邻板就放弃）、`:70-76`（回退为压在自身）；`NativeUI.kt:392-394`（只要选中的拼板已放置，操作条就一直显示）；`MainActivity.kt:95`（没有取消选中的路径）；iOS 对应 `RacingClubApp.swift:179-181, 381`。
- **证据**：我用同一算法把全部 80 关的参考答案摆法（也就是解对之前最后一步的典型局面）离线算了一遍：
  - 单元格约 74dp（接近 1920×1080 模拟器）时，516 块拼板中有 387 块（75%）会落到"压在自身"模式；
  - 单元格约 56dp（620dp 宽屏）时是 427/516（83%）；
  - 80 关里有 76 关至少一块会这样。

  截图也能看到：`android-selection-vertical-v5.png` 中 9 号的道路和横杆几乎被三个按钮全部挡住；`-horizontal-v5` 中 5 号的横杆只露出顶端。
- **用户影响**：解题最后阶段旋转拼板时，恰好看不到正在旋转的那块拼板的道路。这个回退在实际中是常态，不是例外。
- **相关问题**：在 `NativeUI.kt:360`（iOS `:368`），棋盘上已有拼板被选中时，点任意空格会把这块拼板直接移过去，并计一步。帮助文案只说明了"托盘选中后点格子放置"。玩家想点空白处取消选中时，会误移动拼板。
- **修复建议**：
  1. 再点一次已选中的拼板（或点木框边缘、右侧空白）就取消选中、隐藏操作条。点空格放置只对托盘里未放置的拼板生效。
  2. 操作条位置的回退顺序改为：空位 → 允许半透明地覆盖邻板 → 最后才压在自身。压在自身时用更小的按钮，并避开横杆一侧（横杆坐标已知，见 `BoardMaterials.kt:47`）。

  第 2 点仍然满足"按钮在拼板附近"，但和 README 里"避免遮挡邻板"的说法冲突，**需要你确认取舍**。
- **修复风险**：中。需要同步修改 `BoardInteractionTest`、`DragInteractionTest` 里"满盘必须压在自身"一类的断言；"再点取消"要和"按下即选中"配合好（按下时已是选中状态，抬起且没有移动才取消）。
- **验证**：JVM 单测遍历 80 关答案的每一块，断言操作条不覆盖该块的横杆点和道路中线采样点；UI 测试在满盘夹具里点已选中的拼板，确认"拼板操作"节点消失。
- **置信度**：高。

### F-02 [P2] Activity 重建后，玩家会从对局被踢回首页
- **位置**：`MainActivity.kt:118`（`GameState` 只放在 `setContent` 里的 `remember` 中）；`AndroidManifest.xml:4`（只锁了横屏）；`CatalogIntegrationTest.kt:119`（测试把重建后回到首页当作期望）。
- **触发场景**：锁横屏只排除了旋屏。以下情况仍会重建 Activity：
  - 深色模式按日落时间自动切换，而 App 正在前台；
  - 调整系统字号或显示大小后返回 App；
  - 切换系统语言；
  - 平板或折叠屏分屏、窗口尺寸变化。
- **用户影响**：重建后玩家被送回首页。跑动动画中重建的话，结算页丢失（成绩在开始跑动时已经写入，不会丢）。摆放和时间也已在 ON_PAUSE 时保存，丢的是所在页面和弹窗。
- **修复建议**：把 GameState 移进 ViewModel（改用 applicationContext），或者至少把当前页面、关卡 ID、弹窗存进 SavedStateHandle，重建后调用 `start(level)` 恢复。不要用 `configChanges` 来绕开。
- **修复风险**：中。计时基于 `elapsedRealtime`，恢复时要走一遍 pause/resume。
- **验证**：在关卡内执行 `adb shell cmd uimode night yes`，或调用 `scenario.recreate()`，断言仍停留在"挑战 NN"、摆放和计时连续。同时把 `:119` 的期望改成停留在关卡。
- **置信度**：高。

### F-04 [P2] iOS 的对局逻辑和 Android 已经不一致
- **a. 65 关起的端点提示**：`RacingClubApp.swift:37` 没有先存撤销快照，也不判断端点是否已经和答案相同。所以每点一次提示，提示数和步数都会加一，而且这一步撤销不了。Android 对应的 `MainActivity.kt:110` 两点都做了。
- **b. 自动跑动的时序问题**：`:39` 的跑动任务在 250ms 延迟后只检查自己是否被取消，而打开弹窗的 `show()`（`:42`）不会取消它。放下最后一块后立即点帮助或排行榜，跑动会在弹窗打开时开始、成绩被写入。Android 把弹窗状态作为触发条件之一（`NativeUI.kt:108-109`），不会出现这种情况。
- **c. 恢复存档**：`:28` 直接使用存档里的起终点字母，不校验；Android（`MainActivity.kt:93`）会检查字母是否是合法入口。
- **根因**：同一套会话逻辑在两端各写一份，Android 版又依赖 Context、SharedPreferences 和系统时钟，没法写 JVM 单测。计时暂停与恢复、端点撤销、提示计数，两端都没有单测。
- **修复建议**：a–c 可以直接修，工作量小。之后抽出一个不依赖平台的会话模块（时钟和存储由外部注入），Kotlin 和 Swift 各一份实现，共用一组 JSON 场景用例（"操作序列 → 期望状态"），两端测试都跑这组用例。
- **修复风险**：a–c 低；抽取模块为中。
- **验证**：场景"65 关所有提示都给完后再点两次提示，提示数不变，撤销能恢复端点"；场景"放最后一块后 100ms 内打开帮助，关闭弹窗之前不会开始跑动"。
- **置信度**：a、c 高；b 中（需要 iOS 运行时确认时序）。

### F-05 [P2，影响程度需真机确认] Android 进入关卡和拖动时开销偏大
- **进入关卡时主线程解码**：`GameSprites.kt:21-25, 35` 在主线程解码 8 张八向马 PNG（每张约 1.2MB）并逐像素扫描。它的缓存挂在 `NativeUI.kt:329` 的棋盘组件里，所以每次从首页或结算页进入关卡都会重新执行。

- **修复建议**：
  - 材质和马的图片在应用级只加载一次，再往下传；
  - 纹理离线缩小到 256–512px，或改用平铺；
  - 静态棋盘层缓存起来，拖动高亮放到单独的叠层。
- **修复风险**：低到中。纹理缩小后需要和现有截图对比观感。
- **验证**：在低端真机上用 `dumpsys gfxinfo` 看拖动掉帧，用 Macrobenchmark 测"首页 → 进入关卡"的首帧时间，用 `dumpsys meminfo` 看图形内存。

## 可选建议 / 需真机确认（P3）

### F-08 拖动提交依赖全局 `selected`，多指时可能放错拼板
- **位置**：`BoardInteraction.kt:38-44` 和 `MainActivity.kt:97`；`NativeUI.kt:230-231` 按下托盘卡片就改变选中，`:240` 托盘手势结束时会清空拖动状态；iOS 的 `:60、226` 结构相同。
- **场景**：一根手指在棋盘上拖 3 号，同时有另一根手指（例如横握时的右手拇指）按住托盘的 5 号。抬起时放下的是 5 号，3 号留在原处。如果托盘上那根手指先抬起，这次拖动会被静默丢弃。
- **修复建议**：提交时直接使用拖动中那块拼板的 ID；拖动进行中忽略其他手指的按下。
- **修复风险**：低。
- **验证**：仪器测试注入两指按下序列，断言只有 3 号移动。
- **置信度**：中到高（代码路径明确，需要实测确认 Compose 的分发行为）。

### F-09 托盘缩略图是竖的，拖出去默认是横的（需产品确认）
- **位置**：`NativeUI.kt:244`（缩略图固定竖向）；`:232` 和 `MainActivity.kt:95`（未放置拼板默认 0°）；`:107`（移回时不重置朝向）；iOS `:252、227`。
- **用户影响**：从托盘拖出的瞬间，拼板转了 90°。"移回"后直接点空格放置，会沿用移回前的朝向；拖进去则一定是 0°。同一块拼板的朝向取决于用哪种方式放。
- **修复建议**：默认朝向与缩略图一致；移回或选中托盘拼板时统一重置朝向。
- **修复风险**：低到中，需要同步修改 `DragInteractionTest` 的期望值。
- **验证**：托盘拖入、托盘选中后点放、移回后点放三条路径，断言朝向相同。
- **置信度**：高。

## 已考虑并排除
- **已确认的产品决策**：临时重叠和只画顶层、边缘旋转向内移、不提供"全部拼板"、去掉试跑和教学文案、解对自动跑动且可跳过、65 关起端点由玩家选且可相同、托盘竖向按首次出现排序且最多 10 块、目标折行不滚动、只做本机排行榜、服务端只预留契约、固定 release 签名。
- **目标编号不随系统字号放大**（`NativeUI.kt:69`）：这是为了保证所有目标始终可见，和要求 2 一致。
- **Android 每 100ms 的计时刷新和跑动时逐帧重组**：Kotlin 2.2.20 默认开启强跳过，棋盘不会因此整盘重绘，代价很小。
- **按文件长度建议拆分大文件**：不建议；F-04 的抽取有具体的行为差异作为依据。
- **起点/终点标签点击区域小**：Compose 会自动扩大小于 48dp 的点击区域，所以只在 F-10 里提了字号。
- **其他**：
  - 拼板以左上角为锚点旋转，属于"最小内移"规则的一部分；
  - `allowBackup=false` 会让卸载或换机后丢失本机进度和成绩，属于产品取舍；
  - 未使用的图片资源会被 release 构建的资源压缩剔除；
  - 手势导航右边缘返回可能和托盘拖动冲突，但卡片中心离屏幕边缘约 40dp，需真机才能判断。
